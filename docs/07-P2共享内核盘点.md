## 一、为什么要抽

三部曲各自演化至今，同一类"天到底怎么算"的知识已经在三个应用里长出了三份实现。不抽的代价：一处修正（比如宿距星坐标校对、节气精度升级）要改三处，且口径会继续漂移。抽的前提是**行为不变**：本清单按"迁移后各应用验收链全绿"为硬门槛。

## 四、关键架构决策（动手前必须定）

1. **语言与分发**：core 用 TS 源；璇玑是"无前端构建"的原生 ES modules + Electron（Node 22 默认类型剥离在本机可用，但 Electron 内置 Node 版本不保证）。方案 A：core 发布编译后 `.js` + `.d.ts`（璇玑引产物，步天/今时引源）；方案 B：core 只供 TS 应用，璇玑暂不接入。**建议 A**，璇玑接入放在其历法核验之后。
2. **精度口径不合并**：教学近似（J2000、未归算岁差）与精确库（lunar-javascript）并存时，接口必须带 `mode` 字段，UI 层继续向用户声明口径——延续"教学精度/待校对"既定纪律。
3. **迁移顺序**：format → cities → solar → sidereal → lodges → terms（风险递增；terms 等外部核验）。每步迁移后跑三应用各自验收链 + `npm run verify:all`。
4. **行为基线**：迁移前先把现值钉死——步天 astro-check 的数值锚点（GMST 18.697374h 等）就是基线；今时/璇玑补同类锚点断言后再搬。
