# 当前产品决策记录

## D-001：第一版采用无依赖静态原型

- 日期：2026-10-03
- 决策：使用浏览器原生JavaScript、CSS和SVG，不引入后端、账号或外部API。
- 原因：先验证核心体验，降低项目负责人启动和维护成本。
- 代价：暂时没有正式历法内核、云端保存和PNG导出。

## D-002：第一版只做三柱基础体验

- 日期：2026-10-03
- 决策：只展示年柱、月柱、日柱；时柱显示“虚位以待”。
- 原因：避免在时辰未知时生成猜测结果。
- 代价：不能提供完整四柱体验。

## D-003：当前计算采用可解释的近似口径

- 日期：2026-10-03
- 决策：页面明确显示“近似节气口径”，由日期推导三柱和五行，不再使用随机比例。
- 原因：结果需要可解释，同时不能把尚未核验的临界规则当作正式历法结论。
- 下一步：确定年柱分界、节气换月、日柱算法后，接入可审计的数据模块。

## D-004：用户数据只保存在本地

- 日期：2026-10-03
- 决策：使用浏览器localStorage保存最近一次结果。
- 原因：减少隐私风险和后端维护成本。
- 代价：不能跨设备恢复。

## D-011：主要产品形态为 Windows 优先桌面客户端

- 日期：2026-10-04
- 状态：负责人已确认
- 决策：桌面客户端是主要交付物；现有网页静态版本保留为开发预览和备用体验。
- 原因：桌面窗口更符合长期使用、离线和本地保存的产品定位，也能避免把浏览器地址栏、标签页和网页发布流程当成正式产品体验。
- 范围：第一版以输入、今日观象、观象日志、七日复盘为主线；总盘、命盘/五行/命纹、分享、说明与清除是辅助入口；不因为改成桌面就新增账号、同步、托盘或实时服务。
- 验收：需要验证无地址栏单窗口、断网可用、关闭重开能恢复、清除后不恢复、下载/打印和窗口缩放。

## D-012：桌面技术路线分两步

- 日期：2026-10-04
- 决策：先用现有原生 HTML/CSS/JavaScript 做 Electron 开发壳验证；正式安装包、签名和自动更新必须在桌面壳通过内部验收后另行确认。Tauri 只作为后续体积优化备选。
- 原因：Electron 可以复用当前界面和 Node/JavaScript 知识，适合零基础负责人先验证窗口体验；Tauri 需要 Rust、Cargo、Windows 构建工具和 WebView2 管理。
- 安全约束：桌面壳必须关闭 `nodeIntegration`、开启 `contextIsolation` 和沙箱；只加载本地打包资源，禁止远程导航和未审查的新窗口。
- 存储约束：不使用随机端口的临时 HTTP 作为正式桌面存储来源，避免 origin 变化导致 `localStorage` 看似丢失；桌面包优先使用固定本地应用 origin。
- 现在不做：不安装来源不明的打包工具，不购买签名证书，不发布安装包，不把网页 Service Worker 验收当成桌面离线证据。

## D-013：从一次性看盘改为本地观象工作台

- 日期：2026-10-05
- 状态：负责人反馈后执行
- 决策：默认打开“今日观象”，用户选择一个五行行动镜头，记录一件真实发生的事，再在“观象日志”和“七日复盘”中回看。个人盘面保留为“我的底色”，不再承担全部产品价值。
- 原因：单次生成盘面和分享卡只能制造新鲜感，无法证明桌面客户端值得反复打开；本地记录闭环可以在不引入账号、后端或实时 API 的情况下验证持续使用。
- 约束：复盘只做用户记录的描述统计；不生成预测、因果关系、心理诊断或现实建议；日志支持用户主动导出/导入 JSON 和单条删除。
- 下一步：用 3–5 名目标 Windows 用户验证首次记录完成率、第三天回访率和是否理解文化边界，再决定是否做对照、撤销或提醒。
